# MASTER DEVELOPMENT PROMPT

## Build a Production-Ready Laravel Security Firewall Package

You are a senior Laravel package architect, application-security engineer, PHP developer, DevSecOps engineer, and open-source maintainer.

Your task is to design and implement a **production-ready Laravel security package** called:

**Laravel Shield**

Suggested Composer package:

```text
moh-sagor/laravel-shield
```

The package must act as a **defense-in-depth application security firewall for Laravel applications**, protecting both traditional web applications and APIs.

The package must be modular, configurable, performant, testable, extensible, and safe to install into existing Laravel applications without breaking their existing functionality.

---

# 1. CORE OBJECTIVE

Build a Laravel package that can be installed into an existing Laravel application with approximately:

```bash
composer require moh-sagor/laravel-shield
php artisan shield:install
php artisan migrate
```

After installation, the package should automatically provide security protections with minimal manual configuration.

The package must protect against common application-layer threats including:

* SQL injection attempts
* XSS attempts
* Path traversal
* Local file inclusion patterns
* Remote file inclusion patterns
* Command injection patterns
* SSRF attempts
* Malicious HTTP requests
* Suspicious query parameters
* Suspicious request bodies
* HTTP parameter pollution
* Brute-force attacks
* Credential stuffing patterns
* Login abuse
* API abuse
* Excessive request rates
* Application-layer DoS
* Bot/scanner activity
* Malicious file uploads
* Dangerous file types
* MIME spoofing
* File signature mismatch
* PHP/script uploads
* Archive bombs / decompression bombs
* Suspicious archive contents
* Security scanner requests
* Automated probing
* Excessive 404/403 activity
* Security-sensitive route enumeration
* Suspicious user agents
* Header anomalies
* Oversized requests
* Suspicious URL encoding
* Double encoding
* Null-byte attacks
* Basic protocol/request anomalies

The package must NOT claim that it can stop every possible cyberattack.

Clearly separate:

1. Application-layer protection
2. Server-level protection
3. Network-level DDoS protection

The package should provide application-layer protection and integrations/hooks for external WAF/CDN/firewall systems.

# 2. IMPORTANT SECURITY PRINCIPLE

Do NOT build a simplistic keyword-based security system such as:

```php
if (str_contains($input, 'select')) {
    abort(403);
}
```

That approach creates huge false-positive problems.

Instead create a proper security analysis engine.

Every detector should return structured information such as:

```php
RuleResult
```

containing:

```php
[
    'detected' => true,
    'rule' => 'xss.script_tag',
    'severity' => 'high',
    'confidence' => 0.97,
    'score' => 85,
    'message' => 'Potential XSS payload detected.',
]
```

The firewall should combine results and make a final decision.

Possible actions:

```text
allow
log
monitor
throttle
challenge
quarantine
block
```

---

# 3. SECURITY DECISION ENGINE

Implement a central security engine:

```php
SecurityEngine
```

Flow:

```text
Incoming Request
       ↓
Request Normalizer
       ↓
Security Context
       ↓
Detector Pipeline
       ↓
Rule Results
       ↓
Risk Scoring Engine
       ↓
Policy Engine
       ↓
ALLOW / LOG / THROTTLE / BLOCK
```

Create classes such as:

```text
SecurityEngine
SecurityContext
SecurityDecision
SecurityRule
SecurityRuleResult
RiskScore
SecurityPolicy
```

Each rule must be independent.

# 8. SECURITY MODES

Implement:

```text
monitor
balanced
strict
```

### monitor

Detect and log.

Do not block requests except for extremely dangerous cases explicitly configured.

### balanced

Block high-confidence threats.

Throttle suspicious behavior.

### strict

More aggressive protection.

Every mode must be configurable.

# 11. SQL INJECTION DETECTOR

Create:

```php

```

Normalize input before analysis.

Handle:


Do NOT interfere with legitimate Laravel query builders.

# 27. ROUTE OBFUSCATION

Implement the requested feature under:

```text
route_obfuscation
```

Do NOT describe this internally as encryption if it is simply replacing a route with an opaque alias.

Example:

```php
'route_obfuscation' => [

    'enabled' => true,

    'routes' => [
        'admin.users',
        'admin.orders',
        'admin.reports',
    ],

],
```

The original:

```text
/admin/users
```

could become:

```text
/r/X7k29LmP
```

Internally:

```text
/r/X7k29LmP
       ↓
RouteResolver
       ↓
admin.users
       ↓
Controller
```

The mapping must be cryptographically unpredictable.

Do not expose the original route unnecessarily.

# 35. PERFORMANCE

This package will run on potentially every HTTP request.

Performance is extremely important.

DO NOT:

* perform expensive database queries on every request
* scan every request synchronously with external APIs
* write a database row for every normal request
* perform unnecessary DNS lookups
* run antivirus scanning on normal requests
* perform expensive archive processing unless an upload exists

Use:

```text
Redis
Laravel Cache
in-memory configuration
efficient regex
compiled rule definitions
sampling
asynchronous jobs
```

where appropriate.

Security must not destroy application performance.

# 49. SECURITY SCORE

Create a risk score:

```text
0 - 29     LOW
30 - 59    MEDIUM
60 - 79    HIGH
80 - 100   CRITICAL
```

These values must be configurable.

Multiple rules can contribute to the score.

Example:

```text
XSS detected              +40
Known scanner             +20
High request rate         +20
Repeated 404s             +10
```

Then:

```text
Risk = 90
Action = BLOCK
```

Do not use a score as a claim that an attack is definitely malicious.

It represents the package's confidence/risk assessment.
